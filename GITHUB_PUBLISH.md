# Публикация релизов на GitHub

**Статус: подготовка. На GitHub пока ничего не выложено.** Этот файл — план и инструкция на момент
переезда. Своего сервера раздачи у проекта больше нет: обновления будут приходить из GitHub
Releases, модель эмбеддингов уже качается с Hugging Face (см. §2.4).

**Политика по уже установленным сборкам:** мы их не поддерживаем. У кого стоит старая версия с
зашитым адресом нашего сервера — тот просто скачивает новый APK с GitHub и ставит поверх; дальше
обновления приходят уже с GitHub. Миграционных костылей, зеркал и переходных манифестов не делаем.

---

## 1. Что нужно один раз: репозиторий

### 1.1. Секреты в репозиторий не попадают

Публичный репозиторий не должен содержать ключей. Сейчас в git **отслеживаются** (потому что
репозиторий был приватным):

| Файл | Что внутри | Что делать |
|---|---|---|
| `keystore.properties` | пароли хранилища и ключа в открытом виде | убрать из git, оставить локально |
| `keystore/meha-release.jks` | сам релизный ключ подписи | убрать из git, хранить в бэкапе |
| `keystore.md` | пароли, отпечатки, доступ к серверу | убрать из git, держать приватно |
| `local.properties` | путь к Android SDK | уже игнорируется, проверить |

Порядок:

1. В `.gitignore` **удалить** блок с исключениями:

   ```
   # Owner's explicit instruction: this PRIVATE repo intentionally tracks the real release
   # keystore and its plain-text credentials (see keystore.md). Keep these exceptions.
   !keystore/meha-release.jks
   !keystore.properties
   ```

   После этого `*.jks`, `*.keystore` и `keystore.properties` снова игнорируются (правила выше в
   файле уже есть).

2. Убрать файлы из индекса, не удаляя с диска:

   ```bash
   git rm --cached keystore.properties keystore/meha-release.jks keystore.md
   git commit -m "Stop tracking signing secrets"
   ```

3. **История будет обнулена.** Пока файлы лежали в старых коммитах, они остаются доступны через
   `git log`. Поэтому перед публикацией репозиторий создаётся заново с одного снимка:
   ```bash
   rm -rf .git
   git init -b main
   git add .
   git commit -m "Меха: AI-агент для Android"
   ```
   Минус: теряется история коммитов. Плюс: гарантированно нет ни ключей, ни внутренних заметок.
   Переписывать историю через `git filter-repo` не нужно — старых коммитов просто не будет.

4. **Проверить перед первым пушем**, что секретов в индексе нет:
   ```bash
   git ls-files | grep -iE "keystore|\\.jks|\\.properties$|keystore\\.md"
   # ожидаемо пусто (кроме gradle/wrapper/gradle-wrapper.properties и gradle.properties)
   ```

5. **Если ключ всё же попал в публичный репозиторий — он скомпрометирован.** Для этого проекта это
   означало бы смену ключа подписи, а значит невозможность обновить установленные сборки «поверх».
   Поэтому шаг 3 делается **до** первого пуша, а не после.

### 1.2. Создать репозиторий

```bash
gh auth login                      # один раз, вход в GitHub
gh repo create meha --public --source=. --remote=origin --push
```

Если репозиторий создаётся вручную через веб-интерфейс:

```bash
git remote add origin git@github.com:mibazarow/meha.git
git push -u origin main
```

Требования, без которых автообновление не работает:

- репозиторий **публичный** (ассеты приватного репозитория требуют авторизации — клиент получит 404);
- теги и релизы не удаляются;
- имя репозитория и владелец попадают в адрес манифеста (см. §2.1).

## 2. Как устроено автообновление на GitHub

### 2.1. Один адрес, который никогда не меняется

```
https://github.com/mibazarow/meha/releases/latest/download/latest.json
```

- `/releases/latest` — **последний не-draft и не-prerelease** релиз. Черновики и беты в раздачу
  не попадают, пока им не снимут флаг.
- `/download/<имя файла>` — конкретный приложенный к релизу файл.
- GitHub отвечает `302` на `/releases/download/<тег>/<файл>` и затем на CDN
  (`release-assets.githubusercontent.com`). OkHttp следует редиректам по умолчанию, поэтому в
  приложении ничего менять не нужно.

Этот адрес зашит в приложение одной константой:

```kotlin
// app/src/main/java/com/andharness/ru/data/update/UpdateConfig.kt
const val MANIFEST_URL = "https://github.com/mibazarow/meha/releases/latest/download/latest.json"
```

**Пока константа НЕ изменена** — она всё ещё указывает на прежний сервер, потому что репозитория
ещё нет. Переключение делается одной правкой в момент переезда (см. §8 «Чек-лист переезда»).

**Меняется ровно один раз.** Дальше все релизы выкладываются под этим адресом, и старые сборки
видят новые версии автоматически.

### 2.2. Что делает приложение

1. `UpdateClient` делает HTTPS GET манифеста (таймауты 10/20/25 с).
2. `UpdatePolicy.validate` отвергает манифест, если `versionCode <= 0`, `url` не `https://` или
   `sha256` не 64 hex-символа.
3. Если `versionCode` больше установленного — предлагает обновление.
4. `ApkDownloader` качает APK, сверяет **точный размер** и **sha256**, кладёт файл в
   `cacheDir/updates/meha-update.apk`.
5. `ApkSignerVerifier` проверяет, что подпись скачанного APK совпадает с подписью установленного
   приложения. Не совпала — установка не начинается.
6. Установку подтверждает пользователь через системный диалог.

Проверка идёт не чаще раза в 12 часов (кэш в `SharedPreferences`), плюс есть ручная кнопка в
настройках — она всегда ходит в сеть.

### 2.3. Формат `latest.json`

```json
{
  "versionCode": 306,
  "versionName": "1.22.5",
  "url": "https://github.com/mibazarow/meha/releases/download/v1.22.5/meha-1.22.5.apk",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "sizeBytes": 98717979,
  "releasedAt": "2026-11-20T10:00:00Z",
  "notes": "1.22.5 — что изменилось, одной-двумя фразами.",
  "minSupportedVersionCode": 101,
  "mandatory": false
}
```

| Поле | Обязательно | Смысл |
|---|---|---|
| `versionCode` | да | Целое, строго больше предыдущего. По нему сравнивается версия |
| `url` | да | **Прямая ссылка на APK именно этого тега** (`/releases/download/v1.22.5/...`), не на `latest` |
| `versionName` | нет | Показывается пользователю |
| `sha256` | да | 64 hex-символа, регистр не важен |
| `sizeBytes` | нет | Если `> 0`, размер сверяется побайтово |
| `releasedAt` | нет | ISO-8601, для отображения |
| `notes` | нет | Текст «что нового» |
| `minSupportedVersionCode` | нет | Если установленный `versionCode` меньше — обновление считается обязательным |
| `mandatory` | нет | Принудительное обновление |

**Почему в `url` версионный тег, а не `latest`:** манифест лежит в том же релизе, что и APK. Если
указать `latest`, то после выхода следующей версии старый манифест начнёт указывать на новый APK с
другим sha256 — и проверка контрольной суммы провалится. Версионный тег неизменяем.

### 2.4. Модель эмбеддингов

Офлайн-поиск по смыслу использует `embeddinggemma-2` (два GGUF-файла: 309 МБ + 554 МБ). Своего
сервера у проекта больше нет, поэтому источник один — **Hugging Face**:

```
https://huggingface.co/ggml-org/embeddinggemma-2-GGUF/resolve/main/<файл>?download=true
```

Это уже сделано в коде: `EmbedderModelSpec.MODEL.url` и `EmbedderModelSpec.MMPROJ.url` указывают на
Hugging Face, `fallbackUrl` — `null`. `EmbedderSourceSelector` корректно работает с одним
источником.

Если понадобится зеркало (например, Hugging Face станет недоступен), файлы можно приложить к
релизу на GitHub и прописать их адреса в `fallbackUrl` — размеры (309 МБ и 554 МБ) укладываются в
лимит 2 ГиБ на ассет. Контрольные суммы при этом не меняются: файлы должны быть байт-в-байт те же.

## 3. Выпуск релиза: пошагово

### Шаг 1. Поднять версию

`app/build.gradle.kts`:

```kotlin
versionCode = 306          // всегда +1, никогда не переиспользовать
versionName = "1.22.5"
```

`versionCode` — единственное, что влияет на решение «обновлять или нет». Если забыть его поднять,
приложение посчитает сборку той же версией и не предложит обновление, даже если `versionName`
другой.

### Шаг 2. Проверить, что всё зелёное

```bash
./gradlew :app:testSideloadDebugUnitTest
./gradlew :app:detekt
```

### Шаг 3. Собрать релиз

```bash
./gradlew :app:assembleSideloadRelease
```

Готовый файл: `app/build/outputs/apk/sideload/release/app-sideload-release.apk`

Сборка подписана релизным ключом (`CN=Meha`) из `keystore.properties` +
`keystore/meha-release.jks`. Если ключа нет, задача `validateReleaseSigning` **уронит** сборку —
это защита от случайной публикации неподписанного APK. Для сборки нужен файл ключа на машине;
в репозиторий он не попадает.

### Шаг 4. Посчитать размер и хэш

```bash
shasum -a 256 app/build/outputs/apk/sideload/release/app-sideload-release.apk
stat -f%z app/build/outputs/apk/sideload/release/app-sideload-release.apk
```

Первая команда даёт `sha256`, вторая — `sizeBytes`. Обе величины идут в манифест.

### Шаг 5. Переименовать APK

Имя должно быть одинаковым по шаблону, чтобы ссылки не путались:

```bash
cp app/build/outputs/apk/sideload/release/app-sideload-release.apk /tmp/meha-1.22.5.apk
```

### Шаг 6. Собрать `latest.json`

```bash
cat > /tmp/latest.json <<'JSON'
{
  "versionCode": 306,
  "versionName": "1.22.5",
  "url": "https://github.com/mibazarow/meha/releases/download/v1.22.5/meha-1.22.5.apk",
  "sha256": "<sha256 из шага 4>",
  "sizeBytes": <размер из шага 4>,
  "releasedAt": "<UTC, ISO-8601>",
  "notes": "1.22.5 — ...",
  "minSupportedVersionCode": 101,
  "mandatory": false
}
JSON
```

Проверить, что JSON валиден:

```bash
python3 -c "import json;print(json.load(open('/tmp/latest.json'))['versionName'])"
```

### Шаг 7. Создать релиз

```bash
gh release create v1.22.5 \
  --title "1.22.5" \
  --notes "Что изменилось: ..." \
  /tmp/meha-1.22.5.apk \
  /tmp/latest.json
```

Важно:

- **тег** — `v1.22.5` (с префиксом `v`), он же используется в `url` манифеста;
- **не ставить** `--prerelease` и `--draft` для обычного релиза: `/releases/latest` их пропускает;
- оба файла прикладываются к одному релизу — манифест и APK всегда едут вместе.

### Шаг 8. Проверить снаружи

```bash
# 1. Манифест доступен и отдаёт новую версию
curl -s https://github.com/mibazarow/meha/releases/latest/download/latest.json

# 2. APK скачивается по адресу из манифеста и хэш совпадает
curl -sL -o /tmp/check.apk <url из latest.json>
shasum -a 256 /tmp/check.apk
stat -f%z /tmp/check.apk
```

Обе величины должны совпасть с манифестом. Если не совпали — не исправлять манифест поверх
релиза, а выпустить новый релиз с новым тегом и новым `versionCode`.

### Шаг 9. Обновить лендинг

На `bazarow.ru/tools/meha` ссылка на скачивание меняется на
`https://github.com/mibazarow/meha/releases/latest`, версия в бейдже — на новую.

## 4. Правила, которые нельзя нарушать

1. **`versionCode` только растёт.** Уменьшение или переиспользование ломает обновления у всех, кто
   уже поставил версию с большим кодом.
2. **Опубликованный релиз не перезаписывается.** Ни APK, ни `latest.json` в старом теге не
   заменяются. Ошибка исправляется новым релизом.
3. **`sha256` и `sizeBytes` берутся из фактического файла**, а не пишутся по памяти.
4. **Тег в `url` совпадает с тегом релиза.** Иначе ссылка в манифесте уедет на 404.
5. **Релиз содержит ровно два файла:** APK и `latest.json`. Ничего лишнего — это упрощает проверку.
6. **Подпись не меняется.** Тот же `keystore/meha-release.jks`. Другой ключ = приложение не
   установится поверх, потребуется удаление и потеря данных.
7. **Черновики и prerelease не попадают в раздачу** — это можно использовать для беты, но
   помнить, что `/latest` её не увидит, пока не снять флаг.

## 5. Откат и типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Приложение не видит обновление | не поднят `versionCode` | выпустить новый релиз с бо́льшим кодом |
| «Некорректная контрольная сумма SHA-256» | `sha256` в манифесте не 64 hex или от другого файла | новый релиз с правильным хэшем |
| «Сервер обновлений ответил HTTP 404» | тег в `url` не совпадает с тегом релиза, либо релиз draft | проверить тег, снять флаг draft |
| Скачалось, но не устанавливается | подпись APK не совпала с установленным приложением | собрать релизным ключом `CN=Meha` |
| Обновление предлагается повторно после установки | в манифесте `versionCode` равен установленному или меньше | сверить `versionCode` в APK и в манифесте |
| Сломался релиз | — | не трогать старый тег, выпустить следующий релиз |

Проверить, что в APK именно тот `versionCode`:

```bash
~/Library/Android/sdk/build-tools/36.0.0/aapt2 dump badging \
  app/build/outputs/apk/sideload/release/app-sideload-release.apk | head -1
```

## 6. Ограничения GitHub

- **Публичный репозиторий обязателен.** Приватный вернёт 404 на ассеты без токена.
- **До 2 ГиБ на файл релиза.** Наш APK ~99 МБ, запас огромный. Обычные файлы в репозитории
  ограничены 100 МиБ — APK туда не кладём.
- **`/releases/latest` игнорирует draft и prerelease.**
- **Доступность из РФ не гарантирована.** Если у части пользователей GitHub медленный, единственный
  безопасный обход — добавить в клиент второй URL манифеста (сейчас адрес один). Это отдельная
  правка, не входит в переезд.
- **Анонимный лимит API 60 запросов/час на IP** — нас не касается, потому что мы используем
  `releases/latest/download/...`, а не `api.github.com`.

---

## 7. CI: не обязателен

Собирать можно локально, как описано выше. Если захочется автоматизировать через GitHub Actions,
понадобится положить релизный keystore и пароли в **Secrets** репозитория
(`KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`) и декодировать их в workflow
перед сборкой. Это удобно, но добавляет поверхность атаки: секреты становятся доступны любому
workflow в репозитории. Пока релизы редкие, проще и безопаснее собирать вручную.

## 8. Чек-лист переезда (разово)

Выполняется один раз, когда репозиторий готов к публикации.

- [ ] Секреты не в индексе: `git ls-files | grep -iE "keystore|\\.jks|keystore\\.md"` пусто
- [ ] История обнулена: `rm -rf .git && git init -b main && git add . && git commit`
- [ ] Репозиторий создан и публичен: `gh repo create mibazarow/meha --public --source=. --push`
- [ ] `UpdateConfig.MANIFEST_URL` заменён на
      `https://github.com/mibazarow/meha/releases/latest/download/latest.json`
- [ ] `versionCode` поднят, релиз собран и опубликован (§3)
- [ ] Манифест и APK проверены снаружи (§3, шаг 8)
- [ ] Лендинг `bazarow.ru/tools/meha` ссылается на `https://github.com/mibazarow/meha/releases/latest`
- [ ] Прежний сервер раздачи можно выключать: он больше никому не нужен

**Про уже установленные сборки:** мы их не поддерживаем. У кого стоит версия со старым адресом
манифеста, тот скачивает APK с GitHub и ставит поверх — данные сохранятся (тот же `applicationId`
и та же подпись). Дальше обновления приходят уже с GitHub. Переходных манифестов и зеркал не делаем.
